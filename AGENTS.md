# Forbidden Magic: Reforged

Порт Forbidden Magic 0.574 (Minecraft 1.7.10, SpitefulFox) на Thaumcraft 4: Reforged. Логика, числа, рецепты, тексты и ассеты оригинала переносятся 1:1, где это допускает современный API.

Основной трек — main (Minecraft 26.3); mc/26.1.2 и 1.21.1 — самостоятельные треки со своими пинами хоста и релизами. Релизы выходят rolling-каналами release/<версия MC> через release.yml; версионирование — docs/releasing.md.

Этот файл — защитные правила проекта, а не ритуал для каждого изменения. Объём анализа, абстракций и проверок выбирай по реальному риску. Запреты ниже — жёсткие границы проекта; остальное — ориентиры для самостоятельных решений. Трековые ветки носят этот же текст плюс таргет-блок, который уточняет команды и документы своего трека.

## Команды

Из корня репозитория. На Windows заменяй python3 на python; Gradle из Git Bash запускай как `cmd //c gradlew.bat <задача>`.

- Подготовить хост из пина и патчей (обязательно до сборки): `python3 tools/prepare_host.py`; сверить подготовленную копию: `python3 tools/prepare_host.py --verify`
- Собрать аддон: `./gradlew build`
- GameTests: `./gradlew runGameTestServer`; режим без Luxuria: `python3 tools/set_startup_config.py no_lust=true`, затем снова GameTests
- Регенерировать ресурсы: `python3 tools/gen_resources.py`; свежесть — чистый `git diff --exit-code -- src/generated`
- Граница host-agnostic API: `python3 tools/check_host_agnostic_api.py`
- Происхождение JAR: `python3 tools/check_provenance.py`

## Приоритеты

В порядке важности:

1. Правильное игровое поведение и отсутствие регрессий.
2. Совместимость публичного API, registry ID, рецептов, исследований и существующих данных.
3. Корректная интеграция с закреплённой версией хоста.
4. Понятный и сопровождаемый код.
5. Архитектурная универсальность — только когда она решает конкретную задачу.

Предпочитай самое простое решение, которое закрывает задачу и не создаёт проблем для сопровождения. Полезная функциональность важнее абстрактной архитектурной чистоты.

## Цикл работы

- Перед правками проверь текущую ветку, HEAD и состояние рабочего дерева; изучай только нужные для задачи участки.
- Делай небольшие законченные изменения. Планы, design-документы и журналы сессий создавай, когда задача действительно их требует.
- Слои, интерфейсы, capability и конфигурационные флаги добавляй под конкретного потребителя или доказанную границу ответственности.
- Тесты целься в игровую логику, исправленные баги, граничные условия, совместимость данных и регрессии; простые делегации, getter'ы и конструкторы отдельного теста не требуют.
- Проверки подбирай по изменению: начинай с релевантной компиляции или теста, расширяй набор, когда затронуты смежные системы или риск это оправдывает.
- runClient нужен для визуальных и игровых сценариев (модели, рендер, анимации, creative tab, управление), которые нельзя надёжно проверить headless; остальные изменения проверяй тестами.
- Если нужную проверку выполнить нельзя, назови конкретное ограничение. Непроверенный результат не выдавай за подтверждённый.

## Архитектура

Host-agnostic архитектура общего ядра завершена; сохраняй её границы. Абстрагировать каждую новую функцию не требуется. Подробности — docs/architecture/host-agnostic-core.md.

- Модели в core/model, core/aspect, core/recipe и core/research не должны зависеть от Minecraft, NeoForge или API конкретного хоста; границу проверяет CI.
- Общий gameplay-код может использовать Minecraft и NeoForge; прямые зависимости от API Thaumcraft держи в integration/tc4.
- Узкий контракт или capability добавляй, когда реальный общий код вызывает host-specific поведение; поведение только для TC4 допустимо реализовать непосредственно в адаптере.
- Общие определения используй с семантическими ContentId; host registry IDs, сериализаторы, legacy keys и lifecycle-преобразования держи на стороне интеграции.
- Отсутствующую возможность не имитируй похожей механикой: отмечай PARTIAL/UNSUPPORTED там, где это важно для поведения или заявленной совместимости.
- Разные версии Minecraft не объединяй в один source set или бинарник; изменения переноси вертикальными срезами, когда это нужно второму треку.
- Рефакторинг оправдан, когда снижает дублирование, устраняет зависимость, упрощает последующие изменения или исправляет реальную проблему; единообразие само по себе — не повод переписывать работающий код.

Универсальный service locator, god-интерфейсы, многоуровневые фабрики и второй адаптер ради гипотетического будущего хоста запрещены.

## Хост и лицензии

- host.sha фиксирует upstream commit; host/ создаётся скриптом подготовки. Не редактируй host/ вручную: изменения хоста оформляй в patches/*.patch, локальную копию пересоздавай скриптом.
- Рабочее дерево ../thaumcraft-4-reforged оставляй чистым: это upstream-исходник, наши изменения живут только в патчах.
- Не коммить host/ и локальный Maven.
- Thaumcraft 4: Reforged распространяется по All Rights Reserved. Классы и ассеты хоста не должны попадать в JAR аддона; интеграция — только через публичный API. Происхождение JAR проверяет check_provenance.py.
- Обновление host.sha — отдельная осознанная задача: проверь патчи, совместимость API и сборку хоста с аддоном. Попутное обновление с посторонней задачей запрещено.
- Внешние моды интегрируй только через их публичный API и с учётом лицензии; отсутствующую интеграцию не подменяй неоговорённой похожей механикой.

## Ресурсы и данные

- Источники ресурсов — data/ и генераторы tools/; результат — src/generated/. Меняй источник и регенерируй результат; generated-файлы вручную не редактируй.
- Registry ID, ключи исследований, рецептов и сериализации меняй только с проверкой последствий для совместимости.
- Поддерживаемые локали — en_us и ru_ru; обновляй обе, когда изменение добавляет или меняет отображаемый текст.
- no_lust — STARTUP-конфиг: он гейтит саму регистрацию аспекта luxuria, и значения на клиенте и сервере должны совпадать, иначе расходятся ordinal-таблицы аспектов.
- Java и Python: 4 пробела. Комментарии добавляй там, где они объясняют причину, ограничение или неочевидное решение.

## Проверки и публикация

Подбирай проверки по изменению:

- Документация: ссылки и фактические утверждения; сборка обычно не нужна.
- Ресурсы и локализация: структура, ссылки на модели/текстуры и генерация, если менялись её входы.
- Изолированная логика: компиляция и целевой тест.
- Регистрация предметов, рецептов, исследований, lifecycle и host integration: соответствующие GameTests и сборка затронутого трека.
- Клиентские изменения: runClient или конкретная ручная проверка затронутого сценария.

Гейт выполняется автоматически: CI проверяет границу host-agnostic API, сборку, provenance, свежесть ресурсов и GameTests в обоих режимах no_lust; release.yml публикует релиз при пуше в трековую ветку, только если проверки пройдены. Имена workflow своего трека — в таргет-блоке ветки; механизм версионирования — docs/releasing.md. Ручные клиентские проверки визуальных и игровых функций обязательны: headless CI их не покрывает. Результаты одного Minecraft-трека не переноси на другой.

Проверки из release CI не удаляй ради косметического сокращения workflow; оптимизация допустима, когда сохранена эквивалентная защита и есть измеримая причина. Повторять полный гейт локально после каждой мелкой правки не нужно.

- Основной трек живёт в main; mc/26.1.2 и 1.21.1 — самостоятельные трековые ветки. Работай в ветке текущего трека; отдельную изоляцию создавай по запросу пользователя или когда изменение действительно её требует.
- Канон этого файла — main; трековые ветки носят тот же текст плюс таргет-блок (версия Minecraft, пин хоста, имена workflow).
- Историю main не переписывай, force-push не используй; перед записью сверяй актуальный HEAD.
- Добавляй только нужные файлы. Не коммить host/, reference/, run/, временные журналы и локальные конфиги.
- Сообщения коммитов — понятные, английский Conventional Commits предпочтителен; без строк соавторства.
- docs/fidelity.md обновляй при подтверждённом изменении поведения или ограничений; docs/roadmap.md — при изменении реальных незакрытых задач; docs/verification.md — только фактическими результатами проверок.
- Полный паритет не объявляй по одной компиляции или GameTest; для визуальных и боевых сценариев нужна реальная клиентская проверка. И наоборот: не требуй всех ручных проверок проекта для изменения, которое их не затрагивает.
