# Forbidden Magic: Reforged

Порт Forbidden Magic 0.574 на Thaumcraft 4: Reforged. Релиз **2.0.1 для Minecraft 26.3** опубликован. Основной кодовый трек — main; ветки Minecraft 26.1.2 и 1.21.1 остаются отдельными треками.

Этот файл фиксирует защитные правила проекта, а не обязательный ритуал для каждого изменения. Выбирай объём анализа, абстракций и проверок по реальному риску.

## Источники истины

- Поведение и данные оригинала: ../ForbiddenMagic.
- API и исходники хоста: ../thaumcraft-4-reforged; используемый commit закреплён в host.sha.
- docs/fidelity.md — подтверждённые отличия и приближения от оригинала.
- docs/roadmap.md — текущие незакрытые задачи.
- docs/verification.md — последние реальные результаты CI и оставшиеся ручные проверки.
- docs/host-compatibility/thaumcraft-26.3.md — API хоста, который фактически использует основной адаптер.

Читай документы по мере необходимости для затрагиваемой области. Не нужно перечитывать весь набор или создавать отдельный план перед каждой небольшой задачей.

## Приоритеты разработки

В порядке важности:

1. Правильное игровое поведение и отсутствие регрессий.
2. Совместимость публичного API, registry ID, рецептов, исследований и существующих данных.
3. Корректная интеграция с закреплённой версией хоста.
4. Понятный и сопровождаемый код.
5. Архитектурная универсальность — только когда она решает конкретную задачу.

Предпочитай самое простое решение, которое закрывает задачу и не создаёт очевидных проблем для сопровождения. Не откладывай полезную функциональность ради абстрактной архитектурной чистоты.

## Обычный цикл работы

- Перед правками проверь текущую ветку, HEAD и состояние рабочего дерева. Изучай только те участки, которые нужны для задачи.
- Делай небольшие законченные изменения. Не создавай отдельные design-документы, планы и журналы сессий без реальной необходимости.
- Не добавляй слои, интерфейсы, capability или конфигурационные флаги «на будущее». Сначала должен появиться конкретный потребитель или доказанная граница ответственности.
- Не требуй отдельный тест для каждого метода, getter, конструктора или простой делегации. Тесты особенно полезны для игровой логики, исправленных багов, граничных условий, совместимости данных и регрессий.
- Не запускай полный набор проверок после каждой правки. Начинай с релевантной компиляции, проверки или теста; расширяй набор, когда затронуты смежные системы или риск это оправдывает.
- Не запускай клиент Minecraft для изменений, не влияющих на клиентское поведение. Визуальная и реальная игровая проверка нужны для затронутых моделей, рендера, анимаций, creative tab, управления и сценариев, которые нельзя надёжно проверить headless-тестом.
- Если нужную проверку выполнить нельзя, укажи конкретное ограничение. Не выдавай непроверенный результат за подтверждённый.

## Архитектура

В 2.0.0 была завершена заявленная host-agnostic архитектура для общего ядра и текущего Minecraft-трека. Сохраняй её полезные границы, но не превращай их в требование абстрагировать каждую новую функцию.

- Модели в core/model, core/aspect, core/recipe и core/research не должны зависеть от Minecraft, NeoForge или API конкретного хоста.
- Общий gameplay-код может использовать Minecraft и NeoForge. Прямые зависимости от API Thaumcraft оставляй в integration/tc4.
- Добавляй узкий контракт или capability, когда реальный общий код должен вызвать host-specific поведение. Если поведение по смыслу относится только к TC4, его допустимо реализовать непосредственно в TC4-адаптере.
- Не создавай универсальный service locator, god-интерфейсы, многоуровневые фабрики или второй адаптер ради гипотетического будущего хоста.
- Общие определения используй с семантическими ContentId. Host registry IDs, сериализаторы, legacy keys и lifecycle-преобразования держи на стороне интеграции.
- Отсутствующую возможность не имитируй похожей механикой. Отмечай PARTIAL/UNSUPPORTED там, где это важно для поведения или заявленной совместимости.
- Не объединяй разные версии Minecraft в один source set или бинарник. Изменения переноси вертикальными срезами, когда это действительно нужно для второго трека.

Не переписывай работающий код только ради единообразия. Рефакторинг оправдан, когда снижает дублирование, устраняет зависимость, упрощает последующие изменения или исправляет реальную проблему.

## Хост и лицензии

- host.sha фиксирует используемый upstream commit. host/ создаётся через tools/prepare_host.py и не является исходником для ручного редактирования.
- Изменения хоста оформляй в patches/*.patch; локальную копию пересоздавай скриптом подготовки. Не коммить host/ и локальный Maven.
- Thaumcraft 4: Reforged распространяется по All Rights Reserved. Не копируй его исходники или ассеты в аддон и не включай классы хоста в JAR. Используй публичный API.
- Не обновляй host.sha попутно с посторонней задачей. При осознанном обновлении проверь патчи, совместимость API и сборку хоста с аддоном.
- Внешние моды интегрируй только через их публичные API и с учётом лицензии. Не подменяй отсутствующую интеграцию неоговорённой похожей механикой.

## Ресурсы и данные

- Источники ресурсов находятся в data/ и генераторах tools/; результат — в src/generated/. Изменяй источник и регенерируй результат, не редактируй generated-файлы вручную.
- Не меняй registry ID, ключи исследований, рецептов и сериализации без проверки последствий для совместимости.
- Поддерживаемые локали — en_us и ru_ru. Обновляй обе, когда изменение добавляет или меняет отображаемый текст.
- Комментарии добавляй там, где они объясняют причину, ограничение или неочевидное решение. Не комментируй очевидный код ради количества комментариев.

## Проверки и публикация

### Во время разработки

Подбирай проверки по изменению:

- Документация: проверь ссылки и фактические утверждения; сборка обычно не нужна.
- Ресурсы и локализация: проверь структуру, ссылки на модели/текстуры и генерацию, если менялись её входы.
- Изолированная логика: компиляция и целевой тест, если он полезен.
- Регистрация предметов, рецептов, исследований, lifecycle и host integration: соответствующие GameTests и сборка затронутого трека.
- Клиентские изменения: runClient или конкретная ручная проверка затронутого сценария.

### Перед публикацией релиза

Полный релизный гейт для 26.3 должен подтвердить:

1. Подготовку закреплённого хоста, применение патчей и сборку хоста.
2. Сборку аддона и проверку provenance итогового JAR.
3. Актуальность сгенерированных ресурсов.
4. GameTests с no_lust=false и no_lust=true.
5. Ручные клиентские проверки для визуальных и игровых функций, которые headless CI не покрывает.

Для второго version track используй соответствующий workflow и закреплённую версию хоста. Не переноси результаты одного Minecraft-трека на другой.

Полный гейт не нужно повторять локально после каждой мелкой правки: его назначение — подтвердить целостность кандидата на публикацию. При этом не удаляй проверки из release CI ради косметического сокращения workflow. Оптимизировать CI можно, если сохранена эквивалентная защита и есть измеримая причина.

## Git и документация

- main — каноническая ветка для основного трека. По умолчанию работай в ней; отдельную ветку создавай, когда пользователь этого просит или изменение действительно требует изоляции.
- Не переписывай историю main, не используй force-push и перед записью сверяй актуальный HEAD.
- Добавляй только нужные файлы. Не коммить host/, reference/, run/, временные журналы и локальные конфиги.
- Пиши понятные сообщения коммитов; английский Conventional Commits предпочтителен, но формат сообщения сам по себе не должен задерживать полезное изменение.
- Обновляй docs/fidelity.md только при подтверждённом изменении поведения или ограничений. docs/roadmap.md — при изменении реальных незакрытых задач. docs/verification.md — только фактическими результатами проверок.
- Не объявляй полный паритет на основании одной компиляции или GameTest. И наоборот, не требуй всех ручных проверок проекта для изменения, которое их не затрагивает.
